# Kira HRT 数据对接指南（中文）

[English spec](hrt-import-export-protocol.md) · **中文指南**

> 面向**其他 HRT 记录应用的作者**。目标只有两个：
>
> 1. 让你的用户能把记录**搬进 Kira HRT**；
> 2. 让你的应用能读**从 Kira HRT 导出的文件**。
>
> 字段的权威定义见英文规范 [`hrt-import-export-protocol.md`](hrt-import-export-protocol.md)。
> 本文是**怎么做**（字段对照、示例代码、自测步骤、AI 提示词），那份是**字段是什么**。
> 两份不一致时以英文规范为准。

---

## 0. 先看你属于哪种情况

| 你的情况 | 要做什么 | 花多久 |
|---|---|---|
| 你的应用**派生自 Oyama**（或格式相近） | **什么都不用做。**Kira HRT 是从 Oyama 分叉的，你的导出文件我们直接能读。只需告诉用户「导出 JSON，然后在 Kira 里导入」 | 0 分钟 |
| 你的应用是 **Transmtf** | **什么都不用做**，明文和密码加密的 JSON 我们都能读 | 0 分钟 |
| 你的应用是 **Featherline** | **什么都不用做**，`.hrtbackup` 我们直接解密读 | 0 分钟 |
| 你的格式是**自定义**的 | 加一个「导出为 Kira 格式」按钮，见 §3 | 约 30 分钟 |
| 你想读**从 Kira 导出的文件** | 按 §2 解析即可 | 约 20 分钟 |

> **先说结论**：如果你只想让用户「能搬过来」，多数情况**不需要改代码**——先自己试一次
> （§5 有具体步骤），很可能已经能用了。只有当你的导出字段和下面不同，才需要 §3。

---

## 1. 你最少需要提供什么

完整字段表在 §2，但**最少**只要这些就能导入成功：

```json
{
  "format": "kira-hrt",
  "version": 1,
  "events": [],
  "labResults": [],
  "weight": 62
}
```

- `format` — 固定字符串 `"kira-hrt"`。**这是最重要的一个字段**，见 §4.1。
- `version` — 传输协议的版本，写 `1`。本应用自己导出的**完整备份**把版本写在
  `meta.version`（当前是 `3`，见 §2.8）；两种写法导入时都接受。
- `events` — 用药记录（可为空，也可省略）。
- `labResults` — 化验记录（可为空，也可省略）。
- `weight` — 体重，单位**公斤**（可省略）。

**省略的字段不会被碰；传空数组 `[]` 会清空对方的数据。**这条规则很关键，见 §4.2。

## 2. 字段对照表（中文）

### 2.1 时间：`timeH` — 最容易错的一个

**`timeH` 是「自 1970-01-01 00:00:00 UTC 起的小时数」**，不是毫秒，不是日期字符串。

```js
timeH = 毫秒时间戳 / 3600000
```

| 真实时间（UTC） | `timeH` |
|---|---|
| 2025-06-01 12:00 | `485772` |
| 2026-01-01 00:00 | `490896` |
| 2025-09-24 18:30 | `488538.5` |

```js
// 正确
timeH: new Date(record.takenAt).getTime() / 3_600_000

// 错误：直接放毫秒，导入后会变成 1970 年
timeH: new Date(record.takenAt).getTime()
```

> **为什么是小时？** 这是上游 Oyama / Mihari 的单位，本应用沿用。它是个小数，允许
> 半小时、10 分钟这样的精度，所以别取整。

### 2.2 `events[]` — 一条用药记录

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | 字符串 | **是** | 唯一即可，不要求 UUID；在文件内唯一就行 |
| `timeH` | 数字 | **是** | 见 §2.1 |
| `route` | 字符串 | **是** | 取值见 §2.4。不认识的值 → **该行被跳过** |
| `ester` | 字符串 | 建议填 | 取值见 §2.5。不认识的值 → 会被当成 `"E2"` |
| `doseMG` | 数字 | **是** | 毫克，指的是**药物本身**，不是雌二醇当量。见 §4.3 |
| `extras` | 对象 | 否 | 途径相关的细节，见 §2.6 |

### 2.3 `labResults[]` — 一条化验记录

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | 字符串 | **是** | 同上 |
| `timeH` | 数字 | **是** | 同上 |
| `concValue` | 数字 | **是** | 数值 |
| `unit` | 字符串 | **是** | `"pg/ml"`、`"pmol/l"`、`"ng/dl"`、`"nmol/l"` 四选一 |
| `analyte` | 字符串 | **建议** | `"E2"`、`"T"` 或 `"unknown"`：这条化验测的是哪种激素。**请填**；缺失时 Kira 存为 `unknown`，不会按单位猜。 |

前两个单位是雌二醇用的，后两个是睾酮用的。

**`analyte` 是权威字段。** `"T"` 配 `"pg/ml"` 表示一条被误标的睾酮读数——按 T 处理，
不会进入 E2；`"E2"` 配 `"ng/dl"` 同理。缺失或非法值存为 `"unknown"`；unknown 记录会保留，
但**不进入任何校准拟合**（E2、T、背景 E2），直到用户确认类型。这是刻意的：按单位猜，
正是过去让误标 T 读数污染 E2 拟合的原因。

同一张化验单上的**监测项**可以放在同一条记录里（都可选）：
`prolactin`、`prolactinUln`、`alt`、`altUln`、`ast`、`potassium`。

**你不需要填 `monitoringOnly`**——省略 `concValue` 时 Kira 会自动认出这是一条「只含监测项」
的记录。这个字段只是给显式声明用的，外部作者可以完全不管。

> 一条**既没有激素值、又没有监测项**的记录会被丢弃（它没有任何信息可存）。

### 2.3.1 没有 `analyte` 的旧备份

在 `analyte` 字段出现之前导出的备份只有 `unit` + `concValue`。导入时 Kira 会保留全部记录，
但把这些化验标成 `unknown`：它们仍然可见、仍会导出，只是不参与校准。

导入**预览**会在检测到这类记录时提供一个一次性的、需要用户确认的兼容选项：

```
pg/ml、pmol/l -> E2
ng/dl、nmol/l -> T
```

旧备份默认勾选，确认前可以取消。它只作用于这一次导入，不会改写显式 `"unknown"`，
也不会用于在线 API/MCP 写入。不勾选时，这些化验保持 unknown，直到用户逐条编辑并选择 E2/T。

这个映射只是便利，不是证明：旧数据里单位本身错了，导入后仍然是错的。

### 2.4 `route` 的取值（只能这 6 个）

```
sublingual   舌下
injection    注射
patchApply   贴片：贴上
patchRemove  贴片：撕下
gel          凝胶
oral         口服
```

### 2.5 `ester` 的取值（只能这些）

| 值 | 药物 | 参与建模 |
|---|---|---|
| `E2` | 雌二醇（未酯化，凝胶 / 贴片的基准） | 是 |
| `EB` | 苯甲酸雌二醇 | 是 |
| `EV` | 戊酸雌二醇 | 是 |
| `EC` | 环戊丙酸雌二醇 | 是 |
| `EN` | 庚酸雌二醇 | 是 |
| `EU` | 十一酸雌二醇 | 是 |
| `CPA` | 醋酸环丙孕酮 | 否 |
| `SPIRO` | 螺内酯 | 否 |
| `BICAL` | 比卡鲁胺 | 否 |
| `T` | 睾酮（未酯化） | 是 |
| `TC` | 环戊丙酸睾酮 | 是 |
| `TE` | 庚酸睾酮 | 是 |
| `TU` | 十一酸睾酮 | 是 |
| `P4` | 微粉化黄体酮 | 否 |
| `MPA` | 醋酸甲羟孕酮 | 否 |
| `NET` | 炔诺酮 | 否 |
| `RALOX` | 雷洛昔芬（SERM） | 否 |
| `FIN` | 非那雄胺 | 否 |
| `DUT` | 度他雄胺 | 否 |
| `GNRH` | GnRH 类似物 | 否 |

> 「不参与建模」只影响曲线：这些记录照样会存下来、同步、导出，只是药代动力学引擎
> 不给它们画浓度。请**原样传**，**不要**把它们换算成雌二醇或睾酮当量。
>
> `CPA` / `SPIRO` / `BICAL` / `P4` / `MPA` / `NET` / `RALOX` / `FIN` / `DUT` / `GNRH`
> 借用 `ester` 这个字段，是因为一条记录总得说明自己是什么药。

### 2.6 `extras` — 途径细节

只填与 `route` 相关的项，其余省略。**几乎都是数字，只有最后两项是字符串**：

| 键 | 类型 | 适用途径 | 含义 |
|---|---|---|---|
| `sublingualTier` | 数字 | 舌下 | 0–3 = 快速 / 随意 / 标准 / 严格 |
| `sublingualTheta` | 数字 | 舌下 | 吸收比例 0–1（填了它会覆盖 `sublingualTier`） |
| `releaseRateUGPerDay` | 数字 | patchApply | 贴片释放速率，µg/天 |
| `patchWearH` | 数字 | patchApply | 计划佩戴小时数 |
| `gelSite` | 数字 | 凝胶 | 0–3 = 手臂 / 大腿 / 阴囊 / 腹部 |
| `gelProductId` | 数字 | 凝胶 | 1–5 为内置产品，≥1000 为用户自定义产品（见 §7） |
| `gelCoverage` | 数字 | 凝胶 | 0–6 = 产品默认 / 掌1 / 掌2 / 掌3 / 大腿 / 手臂 / 双臂 |
| `gelCoApplied` | 数字 | 凝胶 | 0–2 = 无 / 防晒 / 保湿 |
| `gelWashAfterH` | 数字 | 凝胶 | 涂抹后几小时洗掉 |
| `concentrationMGmL` | 数字 | 凝胶 | 浓度 mg/mL |
| `areaCM2` | 数字 | 凝胶 | 涂抹面积 cm² |
| `patchInstanceId` | **字符串** | patchApply | 这一片的身份，供「撕下」配对；省略时用该记录自己的 `id` |
| `patchRemovalFor` | **字符串** | patchRemove | 「撕下」终止的是哪一次 `patchApply` 的 `id` |

认不出的键会被忽略，不会报错。

### 2.7 可选集合

除了用药与化验，下面这些也能一起搬。规则与 §4.2 相同：**省略 = 不动对方的数据，
传 `[]` = 清空**。

| 集合 | 字段 | 说明 |
|---|---|---|
| `doseTemplates[]` | `id`、`name`、`route`、`ester`、`doseMG`、`extras`、`createdAt`（毫秒）、可选 `label` / `drugId` / `mode` | 保存好的剂量模板，就是首页那一排一键按钮的来源 |
| `journal[]` | `id`、`timeH`、`note`（≤2000 字符） | 体感日记。没有文字的条目不会存 |
| `quickDoses[]` | `id`、`route`、`ester`、`value`、`createdAt`（毫秒） | 快捷剂量按钮，按模式分开 |
| `pkParams` | 对象或 `null` | 用户自定义的药代动力学参数。**`null` 表示「明确清空」**，省略才是「不涉及」 |
| `pkParamsUpdatedAt` | 数字（毫秒） | 上面那项的写入时间戳 |
| `weightUpdatedAt` | 数字（毫秒） | 体重的写入时间戳 |

### 2.8 多模式文件（本应用自己的导出）

本应用可以同时保存「女性化」与「男性化」两套记录，所以自己的完整备份是**多模式**的：

```json
{
  "format": "kira-hrt",
  "meta": { "version": 3, "exportedAt": "2026-10-24T12:00:00.000Z" },
  "mode": "transfem",
  "weight": 62,
  "modes": {
    "transfem": { "events": [], "labResults": [], "doseTemplates": [], "quickDoses": [], "journal": [] },
    "transmasc": { "events": [], "labResults": [], "doseTemplates": [], "quickDoses": [], "journal": [] }
  },
  "events": [],
  "labResults": [],
  "doseTemplates": []
}
```

- `meta.version` 是载荷版本，当前 `3`（加 `journal` 时从 2 升到 3）。
- 顶层的 `events` / `labResults` / `doseTemplates` 是**当前模式**的镜像，方便只读扁平
  结构的一方照样拿到数据。
- 最外层还有 `appState`（设置、自定义凝胶产品目录等），那是本应用自用的，外部作者
  可以整块忽略。
- 写入本应用时两种都行：区分两种模式就用 `modes`，不区分就直接用扁平字段。
- 本应用导出的化验在已知类型时带 `analyte`。在 `analyte` 出现之前导出的旧备份不带；
  导入时除非用户接受 §2.3.1 的一次性单位映射，否则这些化验会保持 `unknown`。

## 3. 怎么加一个「导出为 Kira 格式」

**如果你的应用也是 JS/TS，可以直接用这段**——它把内部记录转成上面的格式：

```js
/**
 * 把内部记录转成 Kira HRT 能直接导入的 JSON。
 * 按你自己的字段名改 INPUT 那几行即可。
 */
function exportForKira(internal) {
  // ── 改这里：你的字段名 ──────────────────────────────────────
  const toEvent = (d) => ({
    id: d.id,
    // 你的时间字段 → 1970 起的小时数。注意除以 3600000，不是原样。
    timeH: new Date(d.takenAt).getTime() / 3_600_000,
    route: d.route,           // 需是 §2.4 的 6 个值之一
    ester: d.drug,            // 需是 §2.5 的值之一
    doseMG: d.doseMg,         // 药物本身毫克数，不是 E2 当量
    extras: d.extras ?? {},   // 没有就给空对象
  });

  const toLab = (l) => ({
    id: l.id,
    timeH: new Date(l.takenAt).getTime() / 3_600_000,
    concValue: l.value,
    unit: l.unit,             // pg/ml | pmol/l | ng/dl | nmol/l
  });
  // ── 上面以下不用改 ─────────────────────────────────────────

  return {
    format: 'kira-hrt',
    version: 1,
    events: (internal.doses ?? []).map(toEvent),
    labResults: (internal.labs ?? []).map(toLab),
    weight: internal.weightKg ?? undefined,
  };
}

// 下载成文件
const blob = new Blob([JSON.stringify(exportForKira(myData), null, 2)],
                      { type: 'application/json' });
const a = document.createElement('a');
a.href = URL.createObjectURL(blob);
a.download = 'for-kira-hrt.json';
a.click();
```

**如果你的应用不是 JS**：按 §2 的表生成 JSON 即可，没有别的约定——不需要特定库、
不需要特定编码、字段名就是表里那些。

## 4. 四个最容易踩的坑

### 4.1 一定要写 `format: "kira-hrt"`

光看字段结构**分不出** Kira 的文件和 Oyama 的文件，因为 Kira 是从 Oyama 分叉的，
两者都有 `meta` / `modes` / `events`。猜错的后果是**静默误读**，而不是报错。
所以请显式写上 `format`。

### 4.2 「省略」和「空数组」意思完全不同

- 文件里**没有** `labResults` 这个字段 → 意思「这份文件不涉及化验」→ **对方现有的化验不动**。
- 文件里写了 `"labResults": []` → 意思「没有化验」→ **对方的化验会被清空**。

所以**只导出用药记录时，请直接省略 `labResults`，不要写成 `[]`**，否则会误删对方的化验数据。

### 4.3 `doseMG` 是药物本身，不是雌二醇当量

这是转换器最常错的一处。

- 2 mg 的**戊酸雌二醇**药片 → `doseMG: 2`、`ester: "EV"`
  —— **不是** `1.53`（那是它的雌二醇当量，只用于模拟，不是记录字段）。
- 12.5 mg 的**醋酸环丙孕酮** → `doseMG: 12.5`、`ester: "CPA"`
  —— 它没有雌二醇当量，也不要编一个。

**按照药盒上印的数字填。**

### 4.4 跳过 ≠ 报错

一个 `route` 或 `timeH` 不合法的行，导入时会被**静默跳过**（不中断整个导入）。
所以导入完成后请核对条数对不对——少了就是这两类字段有问题。

## 5. 怎么测（每一步都具体）

### 5.1 最快的自测：用聊天窗口粘贴

1. 打开 <https://hrt.kiramyao.com/>
2. 进「设置 → 数据管理 → 导入数据」
3. 点「粘贴 JSON 文本」，把生成的内容粘进去
4. 点确定
5. **去「记录」页核对条数和最早/最晚日期**

点「选择文件」也支持文件导入，两种都行。

### 5.2 核对清单

- [ ] 条数和你导出的条数**一致**（少了几条 → 看 §4.4，多半是 `route` 或 `timeH`）
- [ ] 最早那条的日期是你预期的那天（错成 1970 年 → `timeH` 放成了毫秒，见 §2.1）
- [ ] 剂量数字和药盒一致（变小了 → 你填的是雌二醇当量，见 §4.3）
- [ ] 化验记录的数值和单位对得上

### 5.3 有个真实文件更好

如果方便，请**导出一份你自己的真实数据**发给我们（或直接自己走一遍 §5.1）。

这条不是客套：我们对接 Featherline 时，正是用一份真实备份才发现他们的剂量带着浮点
噪声（`12.499934062706513` 这种，本该是 `12.5`）——**这个问题只有真实数据能暴露，
自己造的测试数据里全是整数，永远碰不到。**

把下面整段粘进 Claude Code / Cursor 等带文件读写能力的 AI 助手，让它替你动手：

```

https://github.com/xingqimiao/Kira-HRT-Tracker/blob/HEAD/docs/hrt-import-export-protocol.md

请先读这两份文档，然后：

1. 找到本项目「导出 / 备份」功能的实现位置，告诉我它在哪。
2. 新增一个「导出为 Kira 格式」的选项（不要改掉现有导出，用户可能还在用）。
3. 生成的 JSON 必须满足：
   - 根级 `format: "kira-hrt"` 与 `version: 1`
   - `events[].timeH` 是 1970 起的小时数（毫秒 ÷ 3600000），不是毫秒
   - `events[].doseMG` 是药物本身的毫克数，不是雌二醇当量
   - `route` 只能是 sublingual/injection/patchApply/patchRemove/gel/oral
   - `ester` 只能是文档 §2.5 列出的那些值
   - 本项目没有的字段**直接省略**，不要写成空数组（空数组会清空对方数据）
4. 如果本项目的途径 / 药物名称和文档里的取值不同，写一个映射表转换，并在注释里
   说明每一行映射的依据；无法映射的取值请在导出时跳过并计数，不要硬凑。
5. 改完后把你生成的示例 JSON（5 条以内）贴给我看，我要核对 timeH 和 doseMG。
```

**给 AI 用的注意事项**（也适用于你自己核对）：

- 让它**先读文档再动手**，否则它会自己发明字段名；
- 明确要求「**不要改现有导出**」，否则容易把用户在用的功能改坏；
- 要求它**贴出示例 JSON**，因为 `timeH` 和 `doseMG` 这两个错很难从代码看出来；
- 如果它改完说「已完成」，务必按 §5 实测一遍再采信。

## 7. 已知的差异与限制

- **自定义凝胶产品目录**：现在**能带过来**。凝胶记录用 `gelProductId` 指向一个产品：
  `1–5` 是内置预设，`≥1000` 是用户自定义。导入时如果对方文件里带 `gelProducts[]`
  （或者本应用自己导出的 `appState.settings.gelProducts`），我们会合并进本机目录并
  持久化，记录里的 `id` 因此仍然指得到产品名与浓度。
  仍然保留的差异只有一处：**内置预设的 id 是固定的**，如果对方用了 `1–5` 却是另一个
  产品，那条记录会被解析成我们的预设——请让对方把自定义产品写到 `≥1000`。
- **Oyama 的云备份**（形如 `{"cloud":1,...}`）：它的密钥需要账号的用户 ID 参与，
  任何拿不到该 ID 的人都打不开。请引导用户改用**密码加密导出**的文件。

## 8. 常见的几个问题

**Q：必须用密码加密吗？**
不必。加密是可选的，见英文规范 §10。明文 JSON 我们直接读。

**Q：`version` 该写几？**
传输文件写 `1` 就行；本应用自己导出的完整备份把版本写在 `meta.version`，当前是 `3`
（见 §2.8）。导入时不靠版本号判断格式——`format` 与字段形状才是依据，所以写 `1`
不会丢东西。

**Q：可以只导出一部分记录吗？**
可以。但请注意 §4.2——只导出用药时，**省略** `labResults` 字段，不要写 `[]`。

**Q：一次能导多少条？**
没有硬性限制，但单次导入上限是 20000 条（超过会被拒绝，而不是截断）。

**Q：怎么知道我的文件被正确识别了？**
导入时会先识别格式。不认识的文件会提示「导入失败」；能识别但需要密码的会弹密码框。
如果弹了「输入密码」却打不开，说明密码错了或文件损坏。

**Q：有官方的测试文件吗？**
没有，但 §5.1 的两分钟自测就够用。如果你的格式比较特殊，欢迎提 issue 附一个样例文件。
